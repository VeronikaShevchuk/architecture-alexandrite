# 1. Анализ системы и проблемных точек
## Текущие проблемы производительности:
    - Медленный дашборд MES - операторы жалуются на низкую скорость загрузки списка заказов
    - Долгий расчет стоимости - 2-30 минут на операцию
    - Высокая нагрузка на БД - частые запросы статусов заказов
    - Плохой пользовательский опыт - клиенты недовольны скоростью выполнения заказов

## Ключевые кандидаты для кеширования:  
    Критические для производительности:
        - Список заказов в MES - самый частый запрос операторов
        - Результаты расчета стоимости - дорогие вычисления (2-30 минут)
        - Справочники и конфигурации - редко меняющиеся данные
        - Статусы заказов - частые запросы, редко меняются

    Второстепенные:
        - Данные клиентов для CRM
        - Каталог товаров для магазина
        - 3D-модели после расчета

# 2. Мотивация
## Почему нужно внедрять кеширование:
    Бизнес-проблемы:
        - Потеря операционной эффективности - операторы тратят время на ожидание загрузки дашборда
        - Снижение удовлетворенности клиентов - долгое ожидание расчета стоимости и выполнения заказов
        - Риск потери контрактов - B2B партнеры недовольны скоростью API
        - Ограничение масштабирования - рост на 100 заказов в месяц усугубляет проблемы

    Технические проблемы:
        - Высокая нагрузка на БД - частые сложные запросы к MES DB
        - Дублирование вычислений - одинаковые расчеты стоимости выполняются повторно
        - Неэффективное использование ресурсов - MES API блокируется на долгих операциях
        - Отсутствие горизонтального масштабирования - нет возможности распределить нагрузку

## Ожидаемые результаты от внедрения кеширования:
    Для операторов (MES):
        - Сокращение времени загрузки дашборда: с 10-30 секунд до <1 секунды
        - Увеличение количества обработанных заказов: на 30-50%
        - Улучшение пользовательского опыта: плавная работа интерфейса

    Для клиентов:
        - Сокращение времени расчета стоимости: повторные расчеты мгновенно
        - Ускорение отображения статусов заказов
        - Улучшение общей отзывчивости системы

    Для инфраструктуры:
        - Снижение нагрузки на БД: на 70-80% для кешируемых запросов
        - Увеличение пропускной способности: в 3-5 раз для MES API
        - Улучшение масштабируемости: возможность горизонтального масштабирования

## Элементы системы для кеширования (приоритетный порядок):
1. MES API - список заказов (критично для операторов)
2. MES API - результаты расчета стоимости (дорогие вычисления)
3. Shop API - данные заказов клиентов (B2C опыт)
4. CRM API - статусы заказов (работа продавцов)
5. Справочные данные (материалы, настройки, тарифы)

# 3. Предлагаемое решение

## Тип кеширования: Серверное кеширование с использованием Redis
    Обоснование выбора серверного кеширования:
        - Общие данные для многих пользователей - операторы видят одни и те же заказы
        - Сложные запросы к БД - кеширование результатов тяжелых SQL-запросов
        - Распределенная архитектура - несколько инстансов MES API должны видеть одинаковые данные
        - Необходимость управления инвалидацией - при изменении статусов заказов

    Почему не клиентское кеширование:
        - Данные быстро устаревают - статусы заказов меняются часто
        - Разные представления данных - у каждого оператора свой фильтр/сортировка
        - Сложность синхронизации - изменения должны распространяться мгновенно
        - Ограниченный объем - клиентские устройства не могут хранить все данные

## Паттерн кеширования: Cache-Aside (Lazy Loading)
    Схема работы:
        1. Приложение пытается получить данные из кеша
        2. Если данные есть в кеше → возвращаются сразу
        3. Если данных нет → запрос к БД
        4. Результат сохраняется в кеш
        5. Данные возвращаются приложению

    Обоснование выбора Cache-Aside:
        - Простота реализации - минимальные изменения в коде
        - Устойчивость к сбоям кеша - при падении Redis система продолжает работать
        - Гибкость инвалидации - можно инвалидировать только измененные данные
        - Ленивая загрузка - кешируются только часто запрашиваемые данные

## Почему не другие паттерны
    Write-Through:
        + Гарантированная актуальность данных
        - Увеличивает latency операций записи
        - Сложнее реализовать (нужно менять все write операции)
        - Избыточность для многих сценариев "Александрита"

    Write-Behind (Write-Back):
        + Максимальная производительность записи
        - Риск потери данных при сбое
        - Сложная реализация и отладка
        - Не подходит для финансовых данных (статусы заказов)

    Refresh-Ahead:
        + Предсказуемое время ответа
        - Сложно предсказать паттерны доступа
        - Может кешировать неиспользуемые данные
        - Избыточное потребление ресурсов

## Стратегия инвалидации кеша

**Выбранная стратегия:** Комбинированная (TTL + Event-Driven инвалидация)
    Компоненты стратегии:
        - TTL (Time-To-Live) - автоматическое истечение через заданное время
        - Event-Driven инвалидация - удаление кеша при изменениях данных
        - Паттерн инвалидации по ключу - точное удаление измененных данных
**Сравнительный анализ стратегий инвалидации:**
|Стратегия|	Преимущества|	Недостатки|	Применимость для "Александрита"|
|---|---|---|---|
|TTL (временная)|	Простая реализация, гарантированное обновление|	Возможность stale данных, избыточные запросы к БД|	Для справочных данных, сессий|
|По ключу (точная)|	Максимальная актуальность, эффективность|	Сложная реализация, нужно знать все ключи|	Для заказов, статусов (критично)|
|Паттерн инвалидации|Удаление групп данных, простота|Может удалить лишние данные|Для списков заказов|
|Event-Driven|	Распределенная инвалидация, согласованность|	Сложность инфраструктуры, latency|	Для синхронизации между сервисами|
|Комбинированная (предлагаемый вариант)|	Баланс актуальности и простоты|	Более сложная реализация| Наиболее оптимально для текущих сценариев в компании|

**Обоснование выбора комбинированной стратегии:**
    Для оперативных данных (статусы заказов):
        - Event-Driven инвалидация при изменениях
        - TTL как fallback (на случай пропущенных событий)
        - Гарантированная актуальность + отказоустойчивость

    Для справочных данных (каталог, материалы):
        - Длинный TTL (24 часа)
        - Ручная инвалидация при административных изменениях
        - Баланс между производительностью и актуальностью

    Для результатов расчетов:
        - TTL 1 час (расчеты дорогие, но результаты стабильны)
        - Инвалидация при изменении исходных данных (3D-модели)
        - Возможность принудительного пересчета
