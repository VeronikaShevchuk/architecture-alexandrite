# 1. Мотивация

**Текущая ситуация**

Система "Александрит" столкнулась с критическими проблемами после открытия B2B API:
- Клиенты не получают заказы в срок
- Жалобы на просроченные заказы растут экспоненциально
- Потеряны несколько крупных контрактов
- Операторы не могут эффективно работать из-за медленного MES
- Время релиза увеличилось до нескольких месяцев

**Почему требуется введение мониторинга**

- Проактивное обнаружение проблем - вместо реагирования на жалобы клиентов
- Снижение времени простоя - раннее обнаружение аномалий
- Обоснованное масштабирование - данные для принятия решений о расширении
- Ускорение расследования инцидентов - доступ к историческим данным
- Улучшение SLA/SLO - возможность измерять и гарантировать уровень обслуживания

**Ожидаемая бизнес-ценность**

- Снижение потерь от простоев
- Улучшение клиентского опыта: Снижение жалоб на 60% за 3 месяца
- Сохраняемость контрактов: Предотвращение потери B2B партнеров
- Эффективность команды: Сокращение времени на расследование инцидентов с часов до минут

# 2. Выбор подхода к мониторингу

Предлагается применять комбинированный подход. Для разных компонентов системы предлагается использовать разные подходы:

## 1. Для пользовательских сервисов (Shop API, CRM API) - Четыре золотых сигнала
    - Задержка (Latency) - время обработки запросов
    - Трафик (Traffic) - количество запросов
    - Ошибки (Errors) - частота ошибок
    - Насыщенность (Saturation) - использование ресурсов

## 2. Для системных компонентов (Базы данных, Очереди) - USE метод
    - Utilization - использование ресурсов
    - Saturation - очередь на ресурсы
    - Errors - количество ошибок

## 3. Для бизнес-процессов - RED метод + бизнес-метрики
    - Rate - количество запросов
    - Errors - количество ошибок
    - Duration - продолжительность операций
    - Бизнес-метрики: создание заказов, расчет стоимости, производство

# 4. План действий
**Базовый мониторинг (2 недели)**
- Развернуть Prometheus Stack
- Установить Prometheus + AlertManager на отдельном инстансе
- Развернуть Grafana для визуализации
- Настроить базовые дашборды
- Инструментировать приложения
- Добавить Spring Boot Actuator в Java приложения
- Настроить Prometheus metrics exporter для .NET приложения
- Внедрить RabbitMQ Prometheus exporter
- Настроить мониторинг инфраструктуры
- Node exporter на всех серверах
- PostgreSQL exporter для баз данных
- S3 метрики через CloudWatch/Yandex Monitoring

**Бизнес-мониторинг (3 недели)**
- Внедрить бизнес-метрики
- Создать Order metrics collector
- Реализовать расчет SLA/SLO показателей
- Настроить дашборды для бизнес-команды
- Настроить алертинг
- Определить пороговые значения для критических метрик
- Настроить эскалацию (Slack → PagerDuty → SMS)
- Создать runbook для common проблем

**Расширенный мониторинг (4 недели)**
- Внедрить распределенное трейсинг
- Настроить Jaeger/Zipkin для трассировки запросов
- Инструментировать ключевые бизнес-процессы
- Настроить лог-агрегацию
- Развернуть ELK Stack или Loki
- Настроить парсинг структурированных логов
- Интегрировать с алертингом
- Автоматизация реагирования
- Настроить автоскейлинг по метрикам
- Реализовать автоматические remediation скрипты

# 5. Показатели насыщенности и пороговые значения

## 1. *Критические показатели (SLA нарушение)*
### Расчет стоимости заказа
    Порог: p95 > 15 минут
    Действие:
    - Автоматическое оповещение DevOps и разработчиков
    - Увеличение количества calculation workers в 2x
    - Создание high-priority задачи для расследования

### Очередь RabbitMQ для расчетов
    Порог: >5000 сообщений в очереди price.calculation.request
    Действие:
        - Автоматическое добавление calculation workers
        - Rate limiting для B2B партнеров
        - Уведомление партнеров о повышенной нагрузке

### Доступность MES API
    Порог: Error rate > 5% за 10 минут
    Действие:
        - Автоматический restart проблемных инстансов
        - Переключение трафика на backup регион
        - Оповещение руководителя разработки

## 2. *Предупреждающие показатели*
### Использование памяти БД
    Порог: >85% более 30 минут
    Действие:
        - Оповещение DBA и DevOps
        - Анализ индексов и запросов
        - Планирование вертикального масштабирования

### Количество активных подключений к БД
    Порог: >80% от max_connections
    Действие:
        - Аудит connection pool приложений
        - Оптимизация запросов
        - Увеличение лимитов подключений

### Скорость создания заказов
    Порог: Падение на 30% по сравнению с аналогичным периодом
    Действие:
        - Оповещение бизнес-отдела
        - Проверка маркетинговых каналов
        - Анализ funnel конверсии

## 3. *Процесс эскалации*
### Уровень 1 (Low severity)
    Метрика в предупреждающей зоне >15 минут
    Действие: Уведомление в рабочую группу

### Уровень 2 (Medium severity)
    Метрика превысила порог >5 минут
    Действие: Уведомление в рабочую группу + создание тикета

### Уровень 3 (High severity)
    Нарушение SLA или критический сбой
    Действие: алерт на дежурного инженера + SMS

### Уровень 4 (Critical severity)
    Полный отказ системы
    Действие: Автоматический вызов ответственных лиц + emergency call


# 6. Заключение
Внедрение комплексного мониторинга в "Александрите" является критически важным инвестиционным решением. Без прозрачности и контроля над системой невозможно решить текущие проблемы с производительностью и надежностью.

Предложенный план позволяет начать с быстрых побед (базовый мониторинг инфраструктуры) и постепенно двигаться к продвинутым сценариям (бизнес-метрики, автоматическое реагирование).

Ключевой успех будет зависеть от интеграции мониторинга в ежедневные процессы команды: ежедневный обзор метрик, регулярные ретроспективы по инцидентам, итеративное улучшение пороговых значений, формирование бэклога и систематический его пересмотр с приоретизацией.
