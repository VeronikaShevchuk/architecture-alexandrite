# Проблемные места в архитектуре

## Критические проблемы (блокирующие бизнес)
- Самая критичная проблема — синхронный вызов от B2B API к MES API.На схеме чётко видно: API user напрямую вызывает MES API для расчёта стоимости. Это объясняет, почему после открытия API система падает. При 30-минутном расчёте каждый внешний запрос блокирует поток на 30 минут, вызывает таймауты.
- Отсутствие rate limiting на B2B API - после открытия API система "завалена" запросами
- Медленный дашборд в MES - операторы не видят новые заказы, теряют мотивацию. Проблема с дашбордом MES
MES (React-приложение) загружает список заказов через MES API, который запрашивает данные из MES DB. При большом количестве заказов (особенно с открытием API) этот запрос становится тяжёлым.
- Единая точка отказа (SPOF) во всех компонентах - один инстанс каждого сервиса и БД
- Отсутствие мониторинга и алертинга - проблемы обнаруживаются только по жалобам клиентов

## Структурные проблемы
- Смешанная модель данных - Shop DB используется и Shop API, и CRM API
CRM API и Shop API используют одну БД (Shop DB) — это монолитная связка.
MES API и MES используют свою БД (MES DB) — другой монолит.
Обмен данными между ними только через Messages Queue, но без явной схемы компенсационных транзакций.
- Разделенные статусы заказа - статусы управляются в трех разных системах без единого источника истины
- Отсутствие промежуточного слоя (API Gateway). B2B API-пользователи обращаются напрямую к MES API
- Ручное тестирование и слабый CI/CD - релизы задерживаются на месяцы
- Нет горизонтального масштабирования - монолитные приложения, вертикальное масштабирование ограничено

## Операционные проблемы
- Долгая загрузка 3D-файлов - файлы хранятся в S3, но нет оптимизации
- Отсутствие кэширования - повторные расчеты выполняются заново
- Проблемы с очередями RabbitMQ - нет мониторинга, обработки ошибок
- Нет резервного копирования данных - риск потери заказов

# Инициативы для устранения проблем

## Первые 2-3 мес.
1. Внедрение асинхронного расчета стоимости
    - Создание отдельной очереди для расчетов
    - Разработка workers для обработки задач расчета
    - Изменение API на возврат task_id вместо синхронного ответа

2. Внедрение rate limiting и API Gateway
    - Установка и настройка Nginx/API Gateway
    - Настройка квот для B2B партнеров
    - Защита MES API от прямого доступа

3. Оптимизация дашборда MES
    - Создание материализованных представлений
    - Добавление индексов в MES DB
    - Реализация кэширования частых запросов

4. Настройка мониторинга и алертинга
    - Внедрение Prometheus + Grafana
    - Мониторинг очередей RabbitMQ
    - Алерты на длинные очереди и ошибки

## Следующие 3 мес.

1. Разделение Shop DB на Shop DB и CRM DB
    - Поэтапная миграция схемы данных
    - Создание сихронизации через события
    - Обновление приложений для работы с отдельными БД

2. Создание Order Service как единого источника статуса по заказу
    - Выделение модуля управления заказами
    - Централизация логики статусов
    - Внедрение паттерна Saga

3. Настройка репликации БД и резервного копирования
    - Настройка read-replicas для основных БД
    - Автоматическое резервное копирование
    - План восстановления при сбоях

4. Улучшение CI/CD процесса
    - Автоматизация тестирования (API тесты)
    - Внедрение feature flags
    - Blue-green деплой в prod

## Следующие этапы. Оптимизация и масштабирование (4-6 месяцев)

1. Выделение Calculation Service из MES API
    - Создание отдельного сервиса для расчетов
    - Горизонтальное масштабирование workers
    - Кэширование результатов расчетов

2. Оптимизация работы с 3D-файлами
    - Сжатие файлов при загрузке
    - Streaming для больших файлов
    - CDN для статических файлов

3. Горизонтальное масштабирование приложений
    - Контейнеризация приложений (Docker)
    - Оркестрация (Kubernetes или managed k8s)
    - Настройка auto-scaling

# Обоснование приоритезации инициатив
**Критерии приоритизации:**
- Влияние на бизнес - устранение прямых потерь денег
- Технический риск - вероятность успешной реализации
- Время реализации - скорость получения результата
- Зависимости - что нужно сделать перед другими инициативами

Если бы можно было выполнить только три пункта, я бы выбрала:

1. Внедрение асинхронного расчета стоимости
**Обоснование решения:** Это решает самую болезненную проблему - неспособность системы обрабатывать нагрузку после открытия API. Без этого все остальные улучшения бессмысленны, так как система продолжит "падать".

2. Разделение Shop DB на Shop DB и CRM DB
**Обоснование решения:** Это фундаментальное архитектурное улучшение, которое:
- Устраняет tight coupling между магазином и CRM
- Позволяет независимо масштабировать системы
- Готовит почву для дальнейшей декомпозиции
- Уменьшает риск одновременного отказа обеих систем

3. Улучшение CI/CD процесса с автоматизацией тестирования
**Обоснование решения:** Без этого любые изменения будут опасными и медленными. Автоматизация тестирования и деплоя:
- Позволяет быстро выпускать исправления
- Снижает риск регрессий
- Увеличивает уверенность команды при внесении изменений
- Освобождает QA для более сложных тестов, тем более, что текущий QA практикует написание автотестов

**Общее Обоснование выбора:** Эти три инициативы покрывают:
- Немедленное облегчение (асинхронность)
- Среднесрочную стабильность (разделение БД)
- Долгосрочную эффективность (CI/CD)

Они создают основу для всех остальных улучшений. В первых итерациях необходимо закрыть наиболее острые проблемы, влияющие на финансовую стабильность и репутацию компании. Сначала - снизить градус напряженности и недовольств от основного потребителя, сформировать фундамент для дальнейшего перехода на новую архитектуру.
