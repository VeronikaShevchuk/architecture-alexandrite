# 1. Анализ системы и потенциальных точек отказа

## **Критические точки, где заказ может "сломаться" или зависнуть:**
    
    - Интернет-магазин → Shop API - загрузка 3D файлов, создание заказа
    - Shop API → Messages Queue - отправка сообщения о новом заказе
    - Messages Queue → MES API - обработка расчета стоимости (2-30 минут!)
    - MES API → 3D storage - чтение файлов для расчета
    - MES API → Messages Queue - отправка результата расчета
    - Messages Queue → CRM API - обновление статуса в CRM
    - CRM API → Shop DB - сохранение подтверждения производства
    - MES API → MES DB - обновление статусов производства
    - MES → MES API - интерфейс оператора (медленный дашборд)

## **Системы, которые следует покрыть трейсингом:**

    - Интернет-магазин (Vue)
    - Shop API (Spring Boot)
    - CRM (Vue)
    - CRM API (Spring Boot)
    - MES (React)
    - MES API (C#)
    - Messages Queue (RabbitMQ)
    - Shop DB (PostgreSQL)
    - MES DB (PostgreSQL)
    - 3d files storage (S3)

## Данные для трейсинга
Обязательные данные для каждого спана:
- Trace ID - уникальный идентификатор цепочки
- Span ID - уникальный идентификатор операции
- Parent Span ID - для построения иерархии
- Timestamp - время начала и окончания
- Duration - продолжительность операции
- Service Name - имя сервиса
- Operation Name - название операции

Tags:
- order_id - идентификатор заказа
- user_id - идентификатор пользователя
- status - статус операции
- http.method - HTTP метод (для API)
- http.status_code - HTTP статус код
- error - флаг ошибки
- queue.name - имя очереди (для RabbitMQ)
- db.statement - SQL запрос (сокращенный)
- file.size - размер 3D файла
- polygon.count - количество полигонов в модели
- Бизнес-контекст (в виде логов, привязанных к trace):
- Order creation event - данные о создании заказа
- Price calculation started - начало расчета стоимости
- Price calculation completed - результат расчета
- Manufacturing approval - подтверждение производства
- Manufacturing status updates - изменения статусов производства

# 2. Мотивация

## Почему нужен трейсинг:
- Быстрое расследование инцидентов - вместо часов поиска проблемы по логам разных систем
- Визуализация застрявших заказов - видеть, на каком этапе завис конкретный заказ
- Выявление узких мест - понимание, какие операции занимают больше всего времени
- Мониторинг SLA по заказам - отслеживание времени выполнения всего цикла
- Улучшение взаимодействия команд - единый источник истины при расследовании проблем

## Технические метрики, на которые повлияет трейсинг:
- Время отклика end-to-end - от создания заказа до подтверждения
- Распределение времени по этапам - где тратится больше всего времени
- Процент ошибок на каждом этапе - какие системы чаще всего падают
- Задержки в очередях - время ожидания в RabbitMQ
- Время расчета стоимости - анализ 95-го и 99-го перцентилей

## Бизнес-метрики, на которые повлияет трейсинг:
- Время выполнения заказа - от создания до отправки (цель: 3 недели)
- Конверсия заказов - сколько созданных заказов доходят до производства
- Процент застрявших заказов - заказы, зависшие более 24 часов
- Среднее время расчета стоимости - влияние на пользовательский опыт
- Эффективность операторов - время обработки заказа на каждом этапе

# 3. Предлагаемое решение

## Технологический стек:
- Jaeger - система распределенного трейсинга (open-source, поддерживает OpenTelemetry)
- OpenTelemetry - стандарт для инструментирования приложений
- OTEL Collector - сбор и обработка телеметрии
- Elasticsearch + Kibana - для хранения и визуализации логов, связанных с трейсами

## Компоненты для внедрения:
    1. Tracing Infrastructure (новый компонент)
        - Jaeger All-in-One для разработки и тестирования
        - Jaeger Production Deployment (Collector, Query, UI) для prod
        - OTEL Collector для агрегации данных

    2. Инструментирование приложений:
        - Java приложения (Shop API, CRM API): Spring Boot Starter для OpenTelemetry
        - C# приложение (MES API): OpenTelemetry .NET SDK
        - Frontend приложения: OpenTelemetry JavaScript для браузеров
        - RabbitMQ: OTEL instrumentation для очередей
        - PostgreSQL: OTEL instrumentation для БД

    3. Integration с мониторингом:
        - Экспорт метрик из трейсов в Prometheus
        - Дашборды в Grafana с overlay трейсов
        - Алерты на основе данных трейсинга

# 4. Компромиссы (Случаи, когда трейсинг не принесет пользы)


## Монолитные синхронные вызовы внутри одного процесса
    Если MES API вызывает расчет стоимости синхронно внутри того же процесса
    Решение: Рефакторинг на асинхронную архитектуру с очередями

## Библиотеки без поддержки OpenTelemetry
    Библиотеки для работы с 3D файлами могут не поддерживать OTEL
    Решение: Обернуть вызовы в инструментированные прокси-функции

## Высокочастотные операции
    Сбор трейсов для каждого HTTP запроса может создать нагрузку
    Решение: Использовать sampling (например, 10% запросов)

## Старые версии .NET Framework в MES API
    Если MES API использует .NET Framework 4.x вместо .NET Core
    Решение: Поэтапное обновление или использование сторонних библиотек

## Ограничения по производительности
    Добавление трейсинга может добавить 5-10% overhead
    Решение: Настраиваемый уровень детализации, отключение для внутренних вызовов

## Стоимость хранения данных
    Трейсы занимают много места (особенно с логами)
    Решение: Агрегация, сжатие, организация политики хранения данных (7-30 дней)

# 5. Безопасность. Меры для предотвращения несанкционированного доступа

## Аутентификация и авторизация
    Jaeger UI доступен только через VPN/Corporate network
    Интеграция с корпоративным SSO (Active Directory)
    Ролевая модель доступа:
        - Viewer: Только просмотр (поддержка, операторы)
        - Analyst: Просмотр + поиск + фильтрация (разработчики)
        - Admin: Полный доступ (DevOps, архитекторы)

## Защита данных
    Маскировка PII (Personally Identifiable Information) в трейсах
    Шифрование данных при передаче (TLS 1.3)
    Шифрование данных при хранении
    Регулярное удаление старых трейсов (авто-очистка по разработанной политике)

## Доступ извне
    Нет прямого доступа к Jaeger из интернета
    API для партнеров только через специальный endpoint с rate limiting
    Аудит всех запросов к системе трейсинга
    Конфиденциальность бизнес-данных:
        - Не логгировать цены расчетов в открытом виде
        - Маскировать информацию о клиентах
        - Контроль доступа к трейсам с order_id
