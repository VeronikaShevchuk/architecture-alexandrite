# 1. Анализ системы и необходимых логов
## Системы, требующие сбора логов (отмечены на схеме):
    - Интернет-магазин (Vue) - логи клиентских ошибок
    - Shop API (Spring Boot) - основной источник бизнес-логов
    - CRM (Vue) - логи действий продавцов
    - CRM API (Spring Boot) - логи работы с заказами
    - MES (React) - логи операторов
    - MES API (C#) - критически важные логи расчетов
    - RabbitMQ - логи очередей сообщений
    - Базы данных (PostgreSQL) - медленные запросы, ошибки
    - S3 Storage - логи доступа к файлам

## Список необходимых логов уровня INFO:
    1. Shop API (Spring Boot)
        - Создание заказа: order_id, customer_id, timestamp, 3d_file_size, source (B2C/B2B)
        - Загрузка 3D файла: file_id, size_mb, polygon_count, upload_duration
        - Изменение статуса заказа: order_id, from_status, to_status, timestamp
        - Отправка в очередь RabbitMQ: queue_name, message_id, order_id

    2. CRM API (Spring Boot)
        - Подтверждение производства: order_id, seller_id, timestamp, manufacturing_approved_at
        - Изменение данных клиента: customer_id, field_changed, old_value, new_value
        - Взаимодействие с продавцом: seller_id, action, order_id, duration

    3. MES API (C#)  
        - Начало расчета стоимости: order_id, calculation_started, 3d_file_complexity
        - Завершение расчета: order_id, calculation_duration, calculated_price, success
        - Назначение оператора: order_id, operator_id, assigned_at
        - Изменение статуса производства: order_id, status, operator_id, timestamp

    4. RabbitMQ
        - Получение сообщения: queue, message_id, timestamp, consumer
        - Отправка сообщения: queue, message_id, timestamp, producer
        - Ошибки обработки: queue, message_id, error, retry_count
        
    5. Базы данных
        - Медленные запросы (>1s): query_hash, duration, table, rows_returned
        - Ошибки подключения: database, error_code, timestamp, user
        - Длительные транзакции: transaction_id, duration, queries_count

    6. Frontend приложения (Vue/React)
        - Ошибки загрузки страниц: page_url, error_message, user_agent
        - Ошибки API вызовов: endpoint, status_code, error_message, user_id
        - Действия пользователей: action, element_id, timestamp, session_id

## Уровни логирования и их использование:

    DEBUG - для разработки и отладки
        Детальные SQL запросы с параметрами
        Внутренние состояния объектов
        Временные метки промежуточных операций
        Использование: Только в dev среде, отключено в production

    INFO - нормальная работа системы (основной уровень)
        Бизнес-события (создание заказа, изменение статуса)
        Успешные операции
        Статистическая информация
        Использование: Всегда включен в production

    WARN - потенциальные проблемы
        Медленные операции (> предупреждающего порога)
        Необычные, но обрабатываемые ситуации
        Подозрительная активность
        Использование: Требует мониторинга, но не немедленного действия

    ERROR - ошибки, требующие внимания
        Неудачные бизнес-операции
        Ошибки интеграций
        Исключения в коде
        Использование: Требует расследования

    FATAL - критические ошибки
        Невозможность запуска приложения
        Потеря подключения к критическим ресурсам
        Системные сбои
        Использование: Немедленное реагирование

# 2. Мотивация
## Текущие проблемы:
    Расследование занимает часы/дни - нет структурированных логов
    Невозможно проанализировать тренды - отсутствие исторических данных
    Проблемы обнаруживаются по жалобам - нет проактивного мониторинга
    Сложность отладки распределенных транзакций - нет корреляции логов
    Потеря критической информации при инцидентах

## Что даст внедрение логирования:
    Технические преимущества:
        Сокращение MTTR (Mean Time To Resolution) с часов до минут
        Проактивное обнаружение проблем через анализ паттернов
        Упрощение отладки распределенных транзакций
        Автоматизация расследования через алертинг и корреляцию
        Улучшение observability всей системы

    Бизнес-преимущества:
        Улучшение клиентского опыта - быстрее решение проблем
        Снижение нагрузки на поддержку - меньше ручной работы
        Сохранение репутации - меньше жалоб в соцсетях
        Data-driven оптимизация процессов на основе логов
        Соблюдение SLA - измеримые метрики качества

## Технические метрики, на которые повлияет логирование:
    MTTR (Mean Time To Resolution) - сокращение на 70%
    Процент инцидентов, обнаруженных проактивно - увеличение до 80%
    Время на расследование одного инцидента - сокращение с 4 часов до 30 минут
    Количество ложных алертов - уменьшение на 50%
    Coverage логирования - охват 95% критических операций

## Бизнес-метрики, на которые повлияет логирование:
    Удовлетворенность клиентов (CSAT) - увеличение на 20%
    Количество жалоб на тех. проблемы - снижение на 60%
    Стоимость поддержки на заказ - снижение на 40%
    Конверсия заказов - увеличение на 5% за счет стабильности
    Сохранение B2B контрактов - снижение оттока партнеров

# 4. Предлагаемое решение
[Архитектура системы с логированием](Task4\logDiagram.puml)
## Технологический стек:

    Elastic Stack (ELK) для сбора и анализа логов
    Filebeat - сбор логов с серверов
    Logstash - обработка и парсинг
    Elasticsearch - хранение и поиск
    Kibana - визуализация и дашборды
    Fluentd/Fluent Bit как альтернатива для контейнеризованных сред
    Grafana Loki как легковесная альтернатива для Kubernetes


## Архитектура компонентов логирования:
    1. Filebeat (агенты сбора)
        Установлен на каждом сервере с приложениями
        Собирает логи из файлов (/var/log/*.log)
        Отправляет в Logstash по протоколу Lumberjack
        Конфигурация через Ansible/Puppet

    2. Logstash (обработка)
        Парсинг структурированных логов (JSON)
        Обогащение метаданными (hostname, environment)
        Фильтрация и трансформация данных
        Маршрутизация в разные индексы Elasticsearch

    3. Elasticsearch (хранение)
        Кластер из 3 нод для отказоустойчивости
        Раздельные индексы по системам и дням
        Retention политика: 30 дней для production
        Мониторинг использования диска

    4. Kibana (визуализация)
        Предопределенные дашборды для каждой команды
        Сохраненные поиски для частых сценариев
        RBAC (Role-Based Access Control)
        Интеграция с корпоративным SSO

    5. Log Processor (бизнес-логика)
        Python/Go микросервис
        Чтение логов из Elasticsearch в реальном времени
        Корреляция событий по бизнес-идентификаторам
        Генерация бизнес-метрик и алертов

# 5. Политика безопасности
## Обработка чувствительных данных:
    Маскировка PII (Personally Identifiable Information):
        Номера телефонов: +7 XXX XXX-XX-XX
        Email: user***@domain.com
        Паспортные данные: полная маскировка
        Платежная информация: только последние 4 цифры

    Шифрование данных:
        TLS 1.3 для передачи между компонентами
        Шифрование дисков Elasticsearch
        Шифрование бэкапов

    Контроль доступа:
        Support Team: Только поиск по order_id, email маскирован
        Developers: Полный доступ к техническим логам, ограниченный к бизнес-логам
        Managers: Только агрегированные бизнес-метрики, без PII
        Auditors: Read-only доступ для compliance проверок

    Аудит доступа:
        Логирование всех запросов к Kibana
        Алерты на подозрительную активность
        Регулярные ревью прав доступа

# 6. Анализ логов и алертинг
## Настройка алертинга:
    1. Технические алерты:
            Ошибки в логах: >10 ошибок/минуту в любой системе
            Отсутствие логов: Система не пишет логи >5 минут
            Медленные операции: Запросы >10 секунд в логах
            Падение сервиса: CRITICAL/FATAL логи

    2. Бизнес-алерты:
        Резкий рост ошибок создания заказа: >20% от общего числа
        Увеличение времени расчета: Среднее время >15 минут
        Потеря сообщений в очередях: >5% сообщений в DLQ
        Аномальная активность API: В 10 раз превышает baseline

    3. Security алерты:
        Множественные failed logins: >5 попыток/минуту
        Подозрительные паттерны доступа: Необычные user agents, IP
        Доступ к чувствительным endpoint: Без авторизации
        Аномальные объемы данных: Выгрузка больших объемов

## Обнаружение аномалий:
    Статистические методы:
        Baseline нормальной активности на основе исторических данных
        Скользящее среднее для обнаружения трендов
        Стандартное отклонение для выбросов
        Сезонные паттерны (дневные, недельные)

    Машинное обучение:
        Unsupervised anomaly detection (Isolation Forest, One-Class SVM)
        Time-series forecasting (Prophet, ARIMA)
        Pattern recognition для атак типа DDoS
